## 01 · MPU6050 读不到数据（10/31）

**现象**：程序在跑、舵机回中，但 `pitch/roll/yaw` 恒为 0。

**我问**：为什么程序在跑但读不到角度？

**AI 建议**：别猜代码，先读芯片状态——用 J-Link 读 RAM 里的 `mpu_ready`/`mpu_init_ret`，
再读 I2C 的 `SR1`，最后读 WHO_AM_I。

**我的验证**：

1. `mpu_ready=0`、`mpu_init_ret=10` → 卡在 `mpu_init()`
2. `I2C1_SR1 = 0x200`（AF 位）→ 从机不应答
3. 位翻转 I2C 手动发地址 → 收到 ACK（硬件是通的）
4. 读 `0x75` = **0x74**（正品应为 0x68）→ 兼容芯片，驱动版本自检直接判死

**结论**：在 `inv_mpu.c` 的版本判断里改成"未知版本按普通灵敏度继续"，DMP 正常工作。
**收获**：硬件问题要用寄存器证据定位，不能靠改代码试。

## 02 · Ozone 里变量不刷新（11/10）

**现象**：转模块，Ozone 的 Watch 数值不变，必须暂停再继续才刷新一次。

**AI 建议**：Ozone 的 Watched Data 默认只在 Halt 时更新，要手动开实时刷新；
另外确认加载的 elf 与板子里固件一致。

**我的验证**：按 F5 让程序跑起来 + 打开刷新后，数值连续变化。

**教训**：界面显示 ≠ 芯片真值。后来我改为直接读变量/寄存器来确认状态。

## 03 · 串口链路从 0 到 1（11/12–11/13）

**我问**：上位机要画波形，怎么把数据传出去？

**AI 建议**：先定帧格式再写代码；帧头 2 字节 + 长度 + 命令 + CRC16；
先算带宽（14 B × 100 Hz = 1400 B/s，占 115200 的 12%），确认够用再动手。

**我的验证**：

- 电脑端用 Python 解析，5 秒收到 50 帧、0 校验错
- 用 J-Link 读 `USART1_CR1=0x200C`、`BRR=625`，确认串口初始化正确
- 中间踩过坑：TX/RX 没交叉、MPU 的线被碰松 → 串口"没数据"其实是传感器挂了

**结论**：协议定稿写入 `docs/02-通信协议.md`，代码在 `common/frame.c`。

## 04 · 接 FreeRTOS 后任务建不出来（11/14–11/15）

**现象**：FreeRTOS 窗口只有 2 个任务，`sensorTask`/`commTask` 不见踪影。

**AI 建议**：先确认固件是否真的烧进去（读 flash 里的函数地址），
再查 `configTOTAL_HEAP_SIZE`——每个任务的栈都从堆里分配。

**我的验证**：

- 读 `uxCurrentNumberOfTasks = 2` → 确认只建了 2 个
- 查 `FreeRTOSConfig.h`：`configTOTAL_HEAP_SIZE = 3072` → 只有 3 KB
- 加大到 12 KB、任务栈扩容后，4 个任务齐全

**结论**：`osThreadCreate` 返回值必须检查，否则失败无感知。

## 05 · 一个分号让程序永远进不了调度器（11/15）

**现象**：加了任务创建检查后，担心烧进去会直接卡死。

**AI 指出**：

```c
if (osThreadCreate(...) == NULL);   // ← 分号把 if 结束了
{ Error_Handler(); }                // ← 无条件执行
```

**我的验证**：编译出现 `-Wmisleading-indentation` 警告 → 去掉分号，重新烧录正常。

**教训**：`if (...)` 后面加分号是经典坑；编译器警告要认真看。

## 06 · 接口层用 C 还是 C++（11/16）

**我问**：C 能不能做出"Interface 层"？

**AI 建议**：用函数指针表（ops）模拟虚函数，效果等价；代价是实现结构体的
`base` 必须放第一个成员。

**我的决定**：用 C。理由是驱动库是纯 C、时间紧、C++ 重写收益小。

**验证**：改完后 `main.c` 里只剩 `iuart_send(接口指针, ...)`，不再出现 `HAL_UART_Transmit`。

## 07 · 舵机不动，碰一下地线才动（11/18）

**现象**：上电后云台不补偿；摸舵机臂没有阻力（说明没通电）；碰一下接地排线，舵机会动一下。

**我的排查**：

1. 读 TIM3 寄存器：`CR1=0x81`（CEN=1）、`CCR1=1900`、`CCR2=1100` → PWM 输出正常
2. 摸舵机臂无阻力 → 不是信号问题，是没电
3. 碰地线会动 → 地回路时通时断

**AI 的作用**：提示"先用寄存器判断信号有没有出板子，再查电源"，避免我在代码里乱改。

**结论**：舵机电源的地线接触不良（面包板孔松）。改为适配器负极直接接舵机棕线，再引一根到板子 GND。

## 08 · PID 饱和：动一点就满幅、底座只能转 90°（11/19）

**现象**：底座稍微一动，舵机就以最大幅度纠正，不管动多少幅度都一样；底座转到 90° 顶死。

**排查**：Watch 里读到 `pitch = -66.9°`、`pid_pitch.output = 400`（限幅值）、`servo_pitch_us = 1900`。

**分析（AI 提示 + 我自己算）**：
目标角写死为 0°，而上电时实际姿态是 -66.9° → 误差 66.9° → `8.0 × 66.9 = 535` → 被限幅到 400 → 一直饱和。

**解决**：上电时静止采样 20 次取平均，作为目标角（上电自校准）。

**教训**：闭环的目标值必须来自"当前实际姿态"，不能凭空写 0。

## 09 · MPU 装在面包板上，闭环根本不成立（11/19）

**现象**：无论怎么转云台，姿态只随"整块板子"变化，不随舵机转动变化。

**AI 指出**：从照片看 MPU6050 还在面包板上，没有固定在云台平台上。

**为什么致命**：闭环要求"舵机转 → 平台动 → 传感器测到"。传感器不在平台上，
舵机转多少它都不变 → PID 一路积分到饱和。

**解决**：把 MPU 用双面胶/扎带固定在俯仰平台上。

## 11 · 文档图渲染失败（11/22）

**现象**：电器拓扑用 Mermaid 画，推到 GitHub 后显示"无法渲染富显示"。

**判断**：起初误以为是平台不支持，实际是 Mermaid 语法问题（中文 subgraph、`<br/>`）。

**解决**：改为纯文本方框图，任何平台都能看。

**取舍**：放弃美观度，换渲染稳定性——文档是给人看的，打不开等于没写。
